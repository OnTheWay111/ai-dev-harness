# Web UI 交互设计说明

## 1. 设计目标

Web UI 是生产控制面，不是装饰性 Dashboard。全局首屏必须在十秒内回答三个问题：

> 整体运行是否健康？现在最该处理什么？系统当前正在推进什么？

进入单个 Goal 后，再回答“离安全交付还差哪个决定或哪条证据”。页面默认突出可行动
的信息，不用无法筛选、无法下钻的图表堆满首屏。

## 2. 信息架构

```text
工作台
项目
  Goal Workspace
    需求澄清
    方案与范围
    Issue 计划
    执行与证据
    目标验收
运行中心
执行节点
审计日志
组织设置
```

## 3. 核心页面

### 工作台

- 运行数据统计：待处理、进行中、活跃 Worker、阻塞、今日完成和预算健康。
- 一张统一的全局任务表，同时展示执行进度、待处理问题、Worker、耗时和下一检查点。
- “待处理问题”是任务的异常属性，不再作为与全局任务并列的独立对象。
- 需人工处理的任务置顶，再按业务优先级、截止时间、阻塞影响和等待时长排序。
- 统计卡直接筛选对应队列或进入详情，不展示没有后续动作的“观赏性指标”。
- 无问题任务明确显示“任务正常推进”；异常任务显示问题、排序原因、影响和处理入口。
- Goal 门禁与资源冲突分别建模为门禁任务、调度任务，避免强行绑定到虚假 Issue。
- 主操作“创建新目标”。

### 多 Goal 并行与 Token 调度

界面分为三层：工作台负责全局运营态势和行动入口，全局调度页负责容量与分配解释，
Goal Workspace 只展示当前选中 Goal 的七阶段状态。用户不需要在同一个页面同时
理解多个 Goal 的 Issue、日志和证据细节。

工作台采用“数据统计 + 全局任务表”的简化结构。统计区控制在一行并直接充当筛选器；
全局任务表占满首屏主区，把 Issue 的执行进度和需要处理的问题放在同一行。问题不再
与任务分栏展示：需处理任务自动置顶，无问题任务显示正常推进。点击任务行展开依赖、
证据和工作区，行尾只保留一个与当前状态对应的主操作。健康状态下不展开预算曲线和
固定调度规则；需要解释分配结果时进入独立“全局调度”页。

全局调度页展示跨 Goal 的 Worker 容量、候选队列、领取条件、冲突键、预算曲线和
当前分配理由。它与单个 Goal 的“执行中心”分离：前者回答“系统为什么这样分配”，
后者回答“这个 Goal 正在执行什么”。

全局调度器只从满足以下条件的任务中领取工作：Goal 已通过当前门禁、依赖已完成、
工作区可隔离、影响文件与正在执行任务不冲突。领取顺序综合业务优先级、等待时长、
截止时间、Goal 间公平性和 Token 预算偏差，避免单个 Goal 占满全部 Worker。

Token 使用采用周期预算曲线，而不是简单“跑满并发”：

- 预算使用低于计划时，逐步增加并行槽位，并从 Ready 队列补充测试、Review、文档和验收证据任务。
- 预算使用高于计划时，暂停低价值补充任务，保留高优先级交付路径。
- 默认预留 15% 给最终验收、失败重试和独立 Review；该比例可按组织风险策略调整。
- 不为消耗 Token 创建推测性功能；所有补充任务必须能映射到验收标准、风险降低或可维护性证据。
- 配额数据源可由真实使用量接口、后台导入或人工预算配置提供；原型中的数值仅用于演示。

界面使用“预算健康”和“交付优先”描述调度状态，避免使用可能暗示“为了消耗配额而
运行”的“配额优先”。

每个 Goal 可配置优先级、最大 Worker 数、Token 上限和冲突键。组织层同时配置最大
并行 Goal、最大 Worker、预算周期和最低验收预留。跨 Goal 共享文件默认串行落地。

### Goal Workspace：需求澄清

- 七阶段 Stepper。
- 原始目标、验收标准、非目标和约束。
- Codex 澄清问题和人工回答区。
- 规模/风险建议与解释。
- “保存草稿”“重新生成问题”“确认并继续”。
- 中高风险时明确显示审批人和审批理由。

### Issue 计划审批

- PRD 需求覆盖率、验收覆盖率和 DAG 健康。
- 表格显示依赖、影响模块、冲突、模型能力和推理强度。
- DAG/执行波次切换视图。
- 修改范围、人工模型覆盖和批准动作。
- 被删除过度设计独立展示，避免后续重新引入。

### 执行详情

- Goal 总进度和当前执行波次。
- Worker 卡片：Issue、Builder alias、状态、耗时、Worktree。
- 时间线：Claim、Builder、Verify、Review、Commit、Push、Landing。
- 日志与 Artifact 可搜索，默认脱敏。
- Pause、Stop、Resume 和 Retry 均要求确认；高风险操作要求理由。

### 目标验收

- 每条原始验收标准及其证据。
- 自动化验证、人工验证和未披露风险。
- 失败分类和建议回流阶段。
- Delivery Report 预览与“开发完成，等待验收”通知。

## 4. 交互原则

- 所有异步操作立即返回 receipt，不让浏览器等待模型或执行任务完成。
- 页面刷新后可恢复相同状态，不依赖前端内存。
- 审批必须显示被批准对象的 revision 和 digest。
- 按钮文案描述后果，例如“批准 6 个 Issue 并进入执行”，不用模糊的“确定”。
- 高风险操作使用二次确认和必填理由，普通导航不弹确认框。
- 错误信息包含影响、已保存内容和下一步，不只显示错误码。
- 模型名称隐藏在运行配置详情中；正常界面突出能力等级、成本和风险。
- 无权限操作显示原因和需要的角色，不提供看似可点击的假按钮。

## 5. 视觉方向

- 风格：研发控制室，克制、可靠、证据优先。
- 主色：深海军蓝导航，青绿色表示安全推进，琥珀表示人工门禁，红色表示阻塞。
- 背景：暖灰白，降低长时间阅读疲劳。
- 字体：中文系统无衬线优先，数字和代码使用等宽字体。
- 卡片层级依靠边框、留白和轻阴影，不依靠大面积高饱和渐变。
- 8px 间距基线；输入和主要按钮最小高度 40px。
- 正文和关键辅助信息不低于 12px，表格与列表主要内容使用 13～14px。
- `ink-500` 需满足小字号正文对比度，`ink-400` 仅用于非必要装饰信息。
- 状态不能只依赖颜色，必须同时使用文字和图形标识。

## 6. 响应式与可访问性

- 桌面 1280px 以上为主要生产布局。
- 768～1279px 收起右侧证据栏，保留侧边导航。
- 低于 768px 采用单列查看和审批，不提供复杂 DAG 拖拽。
- 所有操作可键盘访问，焦点清晰。
- 语义化标题、表格、表单 label、live region 和错误关联。
- 文字与背景达到 WCAG AA 对比度。
- 动画尊重 `prefers-reduced-motion`。

## 7. HTML 交互原型

V1 首屏的数据模型、排序口径、接口、异步 receipt 和错误协议见
[Web UI V1 数据模型与接口契约](web-ui-v1-data-api-contract.md)。

原型目录：

```text
prototype/web-ui
```

本地预览运行后访问：

```text
http://localhost:3000
```

原型用于体验信息架构、状态、审批和执行反馈，不连接真实 Codex、AutoDev、GitHub 或生产
数据。浏览器中的模拟状态不能作为后端状态机实现。

设计阶段以该 HTML 原型为视觉和交互基线；Figma 文件
[AI Dev Harness · Production V1 Web UI](https://www.figma.com/design/6SuKnyzfZdEZrWRygQv0w8)
可在具备编辑席位后同步为组件化设计稿。

## 8. 原型验证记录

2026-07-31 已完成以下验证：

- 生产构建、服务端渲染测试和 ESLint 通过。
- 1440 × 1000 桌面布局无横向溢出。
- 390 × 844 移动布局无横向溢出，主导航固定在底部。
- 澄清答案修改、补充问题生成、确认进入方案审批可用。
- Issue 表格与执行波次切换、批准进入执行可用。
- 暂停领取、进入 Goal Verifier、最终证据补齐和 Delivery Report 解锁可用。
- 页面切换会回到顶部，避免移动端继承上一页面滚动位置。

以上只验证设计原型的交互与布局，不代表生产后端、安全或真实 AutoDev/Codex 集成已经完成。
